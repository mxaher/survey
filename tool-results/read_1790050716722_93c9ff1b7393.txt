     4→> **Consultant's note (read before using this prompt):** This merges two build specs that covered the same product from different angles. Where they disagreed, I picked one approach and dropped the other rather than leaving both in — a build agent fed contradictory instructions will guess, and you don't want it guessing on the privacy architecture. The main calls I made:
     5→> - **Lifecycle:** kept the 5-state model (`draft → scheduled → active → closed → archived`) over the simpler 4-state one — it gives you a pre-launch scheduling window, which you'll want for a corporate rollout with a comms date.
     6→> - **Privacy architecture:** kept the HMAC + immutable question-snapshot design over the plainer "participation table" design. It's more work up front but it's the difference between "looks anonymous" and "is architecturally anonymous," which matters a lot given this survey evaluates the CEO and executives.
     7→> - **Question bank:** merged both banks into one library; the admin selects a subset per campaign rather than every question firing every time.
     8→> - **Terminology:** standardized on "campaign" (not "survey") for a single run of this, matching the more rigorous of the two specs, since you'll run this annually and need clean historical comparisons.

   108→## 5. PRIVACY & ANONYMITY ARCHITECTURE — THE MOST IMPORTANT SECTION
   109→
   110→**Core principle:** *Employee identity is used only to establish eligibility and prevent duplicate participation. Survey answers are stored and analyzed completely separately from identity.* This must not merely look anonymous in the UI — the database and API layer must enforce it so that the normal admin workflow cannot ever connect an employee to their answers.
   111→
   112→### 5.1 What must never appear together
   113→Survey response tables (`responses`, environment answers, executive evaluations) must **never** contain: employee name, employee number/code, corporate email, authentication provider ID, phone number, employee HMAC, IP address, user-agent, or device fingerprint. Never put any employee identifier in URLs, query strings, response payloads, `localStorage`, analytics events, or response IDs.
   114→
   115→### 5.2 Two separated layers
   116→
   117→**A. Eligibility / participation layer** (`participation_ledger`) — knows:
   118→- Is this person an authorized, active employee?
   119→- Have they already participated in this campaign?
   120→- Which executives have they already evaluated?
   121→
   122→**B. Response layer** (`responses`) — knows only:
   123→- Which campaign, which executive (if applicable), which question snapshot, which selected value/score, when.
   124→- Linked only via a random, unlinkable `response_group_id` generated at submission time — **not** derived from employee identity.
   125→
   126→### 5.3 The identity token
   127→
   128→Never store a raw employee identifier, a sequential number, or a plain unsalted hash next to responses. Compute a keyed hash server-side:
   129→
   130→```
   131→employee_hmac = HMAC_SHA256(EMPLOYEE_HMAC_SECRET, normalized_employee_identifier)
   132→```
   133→
   134→- `EMPLOYEE_HMAC_SECRET` lives only in Worker secrets; it never reaches the browser or any response record.
   135→- `employee_hmac` is used **only** inside `participation_ledger` to enforce one-participation-per-employee and one-evaluation-per-executive-per-employee. It is never joined to, or stored alongside, `responses`.
   136→- Enforce uniqueness with a real database constraint, not application logic alone:
   137→
   138→```sql
   139→CREATE UNIQUE INDEX idx_participation_unique
   140→ON participation_ledger (campaign_id, employee_hmac, participation_type, scope_key);
   141→```
   142→
   143→Where `scope_key` is the executive ID for executive evaluations, or a fixed literal (`'environment'`, `'future'`) for the other two sections.
   144→
   145→### 5.4 Immutable question snapshots
   146→
   147→At campaign activation, freeze a snapshot of every assigned question and its options into `campaign_question_snapshots` / `campaign_question_option_snapshots`. Responses reference the **snapshot**, never the live, editable question. This is what makes historical results trustworthy even if the reusable question library changes later.
   148→
   149→### 5.5 What this buys you
   150→- Duplicate prevention works even against page refresh, multiple tabs, another browser, direct API calls, or two simultaneous requests (race-condition-safe via the unique index).
   151→- No query an admin can write against the reporting tables can recover who said what.
   152→- If your identity provider or Cloudflare itself retains logs outside this application's database, the README must say so explicitly and describe the system as **de-identified**, not "100% anonymous" — don't let the UI overclaim what the architecture delivers.

   156→## 6. AUTHENTICATION & EMPLOYEE VERIFICATION
   157→
   158→```ts
   159→interface EmployeeIdentityProvider {
   160→  getVerifiedEmployee(request: Request, env: Env): Promise<VerifiedEmployee | null>;
   161→}
   162→
   163→type VerifiedEmployee = {
   164→  externalId: string;
   165→  role?: string;
   166→  department?: string;
   167→  isActive: boolean;
   168→};
   169→```
   170→
   171→Preferred providers, in order: Cloudflare Access → Microsoft Entra ID → existing company SSO → another trusted provider. The verified identifier is used server-side **only** to compute `employee_hmac` — never persisted in plaintext anywhere near responses.
   172→
   173→**Local development mode:** only active when `ENVIRONMENT !== "production"`, must be visibly labeled as dev mode in the UI, must require an explicit flag to enable, and must never expose real production identity data.
   174→
   175→**Admin authentication:** prefer Cloudflare Access / Entra ID / existing SSO. If a temporary password scheme is unavoidable, store only a salted hash (never plaintext), use secure HTTP-only/SameSite session cookies, rate-limit login, expire sessions, support logout, and never ship one shared hardcoded password. Keep it structured so migrating to SSO later is a drop-in change. Employee and admin auth paths must be fully separate — employees can never reach `/admin/*` routes or admin APIs.

   179→## 7. CAMPAIGN LIFECYCLE
   180→
   181→Five states: **draft → scheduled → active → closed → archived**.
   182→
   183→| State | Admin can do | Employee can do |
   184→|---|---|---|
   185→| **Draft** | Everything — add/edit/delete/reorder questions, sections, executives; assign questions to campaign; configure dates, thresholds, rules; preview | Nothing (not visible) |
   186→| **Scheduled** | Edit dates (if not yet started), description, assigned questions/executives; return to draft; cancel | Nothing yet |
   187→| **Active** | View/export reports; close campaign; safely deactivate unused items that don't affect historical data. **Blocked:** deleting questions/executives with responses, changing question wording/type/options that have responses, any structural change that would invalidate historical answers | Participate once; evaluate any number of distinct executives, each once; save/resume if enabled |
   188→| **Closed** | View/export reports (read-only config) | Nothing new; sees "campaign ended" message |
   189→| **Archived** | Fully read-only; excluded from active-campaign selection | N/A |
   190→
   191→On activation: create immutable question/option snapshots (§5.4), record an audit log entry, store `activated_at`, and lock all structurally unsafe edit paths server-side (never rely on the UI hiding a button).
   192→
   193→Confirmation copy before activation:
   194→> "أنت على وشك فتح الاستبيان أمام الموظفين. بعد بدء المشاركة لن تتمكن من حذف الأسئلة أو تعديل بنيتها أو إزالة المسؤولين الذين لديهم إجابات. هل تريد المتابعة؟"
   195→> Buttons: **فتح الحملة** / **إلغاء**
   196→
   197→The architecture must support running this every year (2026, 2027, 2028…) with each campaign keeping its own independent questions, sections, executives, and configuration, and historical campaigns remaining immutable once closed.

   201→## 8. EMPLOYEE EXPERIENCE
   202→
   203→### 8.1 Flow
   204→1. Employee opens the active campaign; identity is verified server-side.
   205→2. Sees campaign title, instructions, and the privacy notice.
   206→3. Completes the **general work-environment** section once (if enabled for this campaign).
   207→4. Sees the executive-selection dropdown: **"اختر المسؤول الذي ترغب في تقييمه"** — populated only with active executives assigned to this campaign, database-driven, never hard-coded.
   208→5. Already-evaluated executives appear disabled/labeled **"تم التقييم مسبقًا"** and move into a **"المديرون الذين تم تقييمهم"** list; the employee picks from the remaining ones.
   209→6. Answers the standardized executive-evaluation questions for the selected executive.
   210→7. Saves that evaluation → executive drops out of the available list → employee may pick another, repeating steps 5–6 for as many executives as they want to evaluate (no forced single-executive limit unless an admin explicitly configures one via `allow_multiple_executive_evaluations`).
   211→8. Completes the **future work-environment** section once (if enabled).
   212→9. Review screen: completion status, number of executives evaluated, names of executives evaluated, and:
   213→   > "بعد إرسال الاستبيان لن تتمكن من إرسال مشاركة أخرى لهذا الاستبيان."
   214→   Checkbox: "أؤكد أن إجاباتي تعكس رأيي المهني وتجربتي في بيئة العمل." Button: **إرسال الاستبيان**.
   215→10. Server re-validates campaign status, executive eligibility, question assignment, and all answer values before accepting.
   216→11. Success page: **"تم تسجيل مشاركتك بنجاح"** — "شكرًا لمشاركتك. تم تسجيل إجاباتك بنجاح." No identity or internal token shown.
   217→
   218→The employee is never limited to evaluating only one executive overall unless the admin has explicitly turned that policy on for the campaign.
   219→
   220→### 8.2 Progress indicator
   221→Show a step indicator across the four sections: 1) بيئة العمل · 2) تقييم القيادات · 3) البيئة المستقبلية · 4) المراجعة والإرسال.
   222→
   223→### 8.3 No free text, anywhere
   224→No `<textarea>`, no comment box, no "other — specify," no written complaint. Every employee answer is one of a predefined, database-stored set of options. This is a hard constraint for v1, not a preference.

   555→## 13. ATOMIC SUBMISSION LOGIC (executive evaluation — apply the same pattern to environment/future)
   556→
   557→1. Verify employee authentication; reject if unverified.
   558→2. Load the campaign; confirm status = `active`.
   559→3. Validate the selected executive is assigned and enabled for this campaign.
   560→4. Validate every required answer against the campaign's question snapshots and option snapshots.
   561→5. Compute `employee_hmac` server-side.
   562→6. Attempt to insert into `participation_ledger`; if the unique index rejects it, return the duplicate-submission error — do not fall through.
   563→7. Generate a fresh random `response_group_id`.
   564→8. Insert `responses` rows with **no** employee identifier of any kind.
   565→9. Make the whole operation atomic (single transaction) or safely idempotent so two concurrent requests for the same employee + executive can never both succeed.
   566→10. Never return `employee_hmac` in any API response.
   567→11. Never log submitted answers or the identifier used to compute the HMAC.

   606→## 16. REPORTING & ANALYTICS
   607→
   608→Aggregated only — **never expose raw response rows to any admin, ever.**
   609→
   610→**Executive report** — per executive, when responses ≥ threshold:
   611→- Number of evaluations.
   612→- Average score per question and per behavioral dimension (respect and professionalism, fairness, communication, listening/psychological safety, empowerment, performance management, development/recognition, collaboration, role-modeling).
   613→- Response distribution per question.
   614→- Favorable-response rate: `count(always + often) / count(valid responses)`.
   615→- Strength areas / improvement areas (highest and lowest dimension scores).
   616→- Not-applicable counts (excluded from averages).
   617→- Comparison to the organization-wide average where meaningful.
   618→- Trend vs. prior campaigns, once more than one exists.
   619→
   620→**Organization report:**
   621→- Overall environment index.
   622→- Question-level distributions across the 8 work-environment dimensions (respect & fairness, communication, leadership, empowerment, development, collaboration, psychological safety, role/goal clarity).
   623→- Top improvement priorities and preferred future-environment themes (from §10.3).
   624→- Positive / neutral / negative percentage breakdown per dimension, not just the average.
   625→
   626→**Do not rank executives.** No "best manager," no leaderboard, no #1/#last. Present each executive's profile neutrally, framed around development, not competition.
   627→
   628→**Minimum sample size:** default **5**, admin-configurable. Below threshold: hide detailed results and show "لا تتوفر بيانات كافية لعرض النتائج حالياً حفاظاً على سرية المشاركين." Apply the same suppression rule to any future demographic segmentation (department, tenure, etc.) if that's ever added.
   629→
   630→**Scoring formulas** (document in the README, in Arabic, exactly as implemented):
   631→```
   632→average_score = sum(valid_scores) / count(valid_scores)     // not_applicable excluded
   633→favorable_rate = count(always_or_often) / count(valid_responses)
   634→```
   635→
   636→Admin dashboard (`/admin/dashboard`, `/admin/reports/:campaignId`): active campaign & status, environment/future/executive response counts, number of executives evaluated, participation rate (if eligible population is knowable), last update time — **no identity-level records ever surfaced.**

   650→## 18. SECURITY REQUIREMENTS
   651→
   652→- Secure, HttpOnly, SameSite session cookies where sessions are used; CSRF protection on all state-changing requests.
   653→- Server-side authorization on every route — never trust a frontend check as the security boundary.
   654→- Input validation via schemas; parameterized D1 queries only.
   655→- Rate limiting on submission and admin-login endpoints.
   656→- Secure headers, CSP where practical.
   657→- No sensitive data in URLs or query strings.
   658→- No third-party tracking/analytics scripts on employee-facing survey pages.
   659→- `Cache-Control: no-store` on all employee and submission endpoints.
   660→- Re-validate campaign status, executive eligibility, and question assignment on every submission — never trust client-supplied state.
   661→
   662→**Never log:** employee name, email, employee code, `employee_hmac`, survey answers, full request bodies, raw auth tokens.
   663→**Safe to log:** route, an anonymous request ID, campaign ID, executive ID (where operationally needed), error category, timestamp.
